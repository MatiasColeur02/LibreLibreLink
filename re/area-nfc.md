## 1. Summary

1. The NFC layer is a thin ISO 15693 (NfcV only) transport. All sensor commands are raw `NfcV.transceive` byte arrays that start with request flags `0x02` (high data rate, non-addressed), then a command code, then the IC manufacturer code taken from UID byte 6 (`0x07`, default `7` when no tag). Response byte 0 is the ISO 15693 response flags; bit0 set means error.
2. Two NFC modules exist and are selected **per sensor from `patchInfo`**, not from the product marketing name: `DefaultNfcRfModule` (Gen1/"no extra security", `rfGen1`) and `DefaultNfcRfModuleGen2` (`rfGen2`). The selector is `DefaultSensorAbstractionService.getSecurityGeneration(patchInfo)`, which reads only `patchInfo[2]`: high nibble 3 and low nibble `>= 9` gives Gen2; high nibble 7 and low nibble `>= 4` gives Gen2; high nibble 3 low `< 9` or high 7 low `< 4` gives Gen1; anything else (or `patchInfo.length < 6`) gives 0, which makes `getRfModule` pick Gen1 as well.
3. `patchInfo` itself is always read with the same command `02 A1 <mfr>` through the Gen1 module (`rfGen1.getPatchInfo`) before the generation is known, so identity/patchInfo is not security-gated. Serial number = base32-like encoding of the 8-byte UID (Android byte order) prefixed by one char of the native `getProductFamily(patchInfo)` index.
4. The streaming enable command is `02 A1 07 <payload>` (Gen1; payload is computed natively and the 6 reply bytes after the flag byte are the sensor BLE address) or an authenticated 19-byte `02 A1 07 1E ...` (Gen2; the 19 bytes are produced by the native Gen2 engine from a sensor-supplied challenge, and the reply goes back into the native engine to extract a 12-byte "streaming authentication data" blob and the 6-byte BLE address).
5. Product-support gating is a per-country build config (`assets/config/ES_bld_cfg.json`): `ProductType0 = "0,3"`, `ProductType3 = "0,1,2,5,6,7,9,A,B"`, type-7 literally `0` in the DI wiring. In this ES build, type-3 generations `9,A,B` are the Gen2-security sensors; type-3 generations `0,1,2,5,6,7` go the Gen1 route.
6. Verdict on the key question: **in this app a Libre 2 Plus goes through the Gen2 path only if its `patchInfo[2]` is `0x39..0x3F`; with `patchInfo[2] = 0x31` it goes through the Gen1 path.** The APK alone does not contain a Libre 2 Plus patchInfo, so the model-to-generation mapping is external: [ext] DiaBLE annotates the EU Libre 2+ patchInfo as `C6 09 31 01` / `7F 0E 31 01` (low nibble 1, Gen1, labeled "non-Gen2 European Libre 2+") and the US/LA Libre 2+ as `2C 0A 3A 02` / `2B 0A 3A 08` (low nibble `A`, Gen2). The deciding experiment is to read the user's own `patchInfo` (6 bytes) from the iPhone. See section 7.

Actors: iPhone/Android reader (R), sensor (S), `SAS` = `DefaultSensorAbstractionService`, `NATIVE` = `libDataProcessing.so` via `DataProcessingNative`.

## 7. Verdict for the key question: is Gen2 used for a Libre 2 Plus?

- **O**: The decision is purely `patchInfo[2]`. In this ES build (supported type-3 generations `0,1,2,5,6,7,9,A,B`), the sensor takes the Gen2 NFC module and the P1/P2 engine iff the low nibble is `9`, `A` or `B` (ev_4e3517698b3911fa1a1aa4f593606d44677e614648430434632a11b615035973, ev_73db8daab32b90024eb0422237919849b4c256a0c533b34573ea14b5587818c7, `ES_bld_cfg.json`).
- **[ext]** DiaBLE's field notes list the EU Libre 2 Plus as patchInfo `C6 09 31 01` or `7F 0E 31 01` (`patchInfo[2] = 0x31`, low nibble 1) and the US/LA Libre 2 Plus as `2C 0A 3A 02` / `2B 0A 3A 08` (`0x3A`). With the app's own thresholds this makes an **EU (Spanish) 15-day Libre 2 Plus a Gen1-security sensor and a US/LA Libre 2 Plus a Gen2 sensor**.
- **Answer**: "Does a Libre 2 Plus go through the Gen2 security path?" -> not by product name; **it depends on the sensor's `patchInfo[2]`, and the evidence points to NO for an EU Libre 2 Plus (0x31) and YES for a US/LA one (0x3A)**. The EU claim rests on an external reference and is unverified for the user's actual sensor. This differs from area-native's assumption that the Plus "almost certainly needs P1/P2"; the Java gating shows Gen1 sensors never reach P1/P2 for NFC (P1/P2 are also not used on the Gen1 BLE path). Whether the Gen1 natives (`getEnableStreamingPayload`, `getStreamingUnlockPayload`) are themselves SKB-gated is a native question (area-native: no SKB at depth 1 for `getEnableStreamingPayload`).
- **Deciding test (cheap, no risk)**: with the iPhone, send ISO 15693 custom command `A1` (flags `0x02`, mfr `0x07`, no parameters) to the user's sensor and read the 6-byte reply. If `reply[2] >> 4 == 3` and `reply[2] & 0x0F < 9` -> Gen1 path. This is a read-only query (the same call `scanSensor` makes first).
